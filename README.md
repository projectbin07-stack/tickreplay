# tickreplay

[![CI](https://github.com/projectbin07-stack/tickreplay/actions/workflows/ci.yml/badge.svg)](https://github.com/projectbin07-stack/tickreplay/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

A small, deterministic, event-driven backtesting and paper-trading research engine in
pure Python. No runtime dependencies beyond the standard library.

> **Disclaimer.** tickreplay is research and education software. It simulates trading;
> it does not trade. Every number in this repository comes from **synthetic data**
> produced by a seeded random-number generator, under simplified fee, slippage and fill
> assumptions. Nothing here is financial advice, a recommendation, or evidence that any
> strategy is profitable. The two bundled strategies are examples of the API, not
> suggestions. **Live trading is out of scope:** there is no exchange connectivity and
> no wallet, key or credential handling anywhere in the code.

## Why it exists

Most backtesting bugs are not exotic. They are a strategy quietly reading a bar it could
not have seen yet, a float drifting a cent per thousand trades, or a run that cannot be
reproduced a week later. tickreplay is a compact codebase (about 1,500 statements) built
to make those three failure modes hard:

- **No look-ahead by construction.** Orders fill no earlier than the open of the bar
  after the one the strategy acted on, and a test proves it.
- **Exact accounting.** Cash, positions and P&L use `decimal.Decimal`; the identities
  `equity == cash + position value` and
  `equity == initial cash + realised + unrealised - fees` are asserted with `==`, not
  `approx`.
- **Reproducible runs.** Events are ordered by timestamp and then by an insertion
  sequence number. A run produces a SHA-256 digest of its fills and equity curve; the
  same inputs give the same digest.

It is meant to be read, modified and used for experiments, not to compete with
full-featured frameworks.

## Features

- **Event model** - immutable typed events (`Bar`, `Trade`, `Signal`, `Order`, `Fill`)
  on a priority queue ordered by `(timestamp, sequence)`.
- **Data** - strict CSV readers for bars and trade ticks (positive prices, consistent
  OHLC, monotonic timestamps, line-numbered errors) with gap *reporting*; seeded
  synthetic generators (geometric Brownian motion and a mean-reverting
  Ornstein-Uhlenbeck process) whose output is labelled as synthetic in the file itself.
- **Execution simulator** - market, limit and stop orders; next-bar-open fills;
  fixed + proportional fees; fixed-bps and volume-participation slippage; partial fills
  capped at a fraction of bar volume.
- **Portfolio accounting** - positions, average cost, realised/unrealised P&L, cash,
  equity curve and flat-to-flat round trips, long and short.
- **Risk layer** - max position size, max gross exposure, per-trade risk sizing from a
  stop distance, and a daily loss limit that halts new exposure (optionally flattening).
- **Strategy API** - `on_start`, `on_bar`, `on_fill` (plus `on_trade` for tick feeds),
  with two reference strategies: SMA crossover and Donchian breakout.
- **Metrics** - total return, CAGR, volatility, Sharpe, Sortino, max drawdown and its
  duration, win rate, profit factor, exposure, turnover. Each is tested against values
  worked out by hand.
- **Paper-trading mode** - the same engine and simulator driven by a pluggable feed.
  The only feed shipped replays a CSV in real or accelerated time.
- **CLI** - `tickreplay gen | run | compare | paper`, with a self-contained HTML report
  (inline SVG equity curve and drawdown, no CDN, no external requests).

Requires Python 3.10 or newer. tickreplay is not published on PyPI; install from source:


### CLI reference

```console
$ tickreplay --help
usage: tickreplay [-h] [--version] {gen,run,compare,paper} ...

Deterministic event-driven backtesting and paper-trading research engine.
Simulation only: no exchange connectivity, not financial advice.

positional arguments:
  {gen,run,compare,paper}
    gen                 generate seeded SYNTHETIC bar data
    run                 backtest one strategy over a bar CSV
    compare             backtest several strategies on the same data
    paper               paper-trade a strategy against a replayed CSV

options:
  -h, --help            show this help message and exit
  --version             show program's version number and exit
```

`run`, `compare` and `paper` share the engine options: `--cash`, `--fee-bps`,
`--fee-fixed`, `--slippage-bps`, `--impact-bps`, `--participation`, `--allocation`,
`--qty-step`, `--price-tick`, `--max-position`, `--max-gross-exposure`, `--risk-per-trade`,
`--daily-loss-limit`, `--flatten-on-halt`, `--periods-per-year`. Strategy parameters are
passed as `--param fast=5 --param slow=20` (SMA) or `--param entry=20 --param exit=10`
(Donchian). `tickreplay <command> --help` lists everything.

### Bringing your own data

Bar CSV: `timestamp,open,high,low,close,volume` with an optional `symbol` column.
Tick CSV (Python API only): `timestamp,price,size` with an optional `symbol` column.
Timestamps are ISO 8601 (naive values are read as UTC) or integer epoch seconds; a bar's
timestamp is its **open** time. Lines starting with `#` are kept as data notes and shown
in the report. Whatever data you load, the results are still a simulation.

### Writing a strategy

```python
from decimal import Decimal

from tickreplay import Bar, Direction, EngineConfig, FeeModel, Strategy, StrategyContext
from tickreplay import compute_metrics, run_backtest
from tickreplay.data import gbm_bars


class AboveOpen(Strategy):
    """Toy rule: long after an up bar, flat after a down bar."""

    name = "above-open"

    def on_bar(self, ctx: StrategyContext, bar: Bar) -> None:
        if bar.close > bar.open and ctx.position(bar.symbol) == 0:
            ctx.signal(bar.symbol, Direction.LONG)
        elif bar.close < bar.open and ctx.position(bar.symbol) > 0:
            ctx.signal(bar.symbol, Direction.FLAT)


bars = gbm_bars(seed=1, n=500)  # synthetic
result = run_backtest(bars, AboveOpen(), EngineConfig(fees=FeeModel(rate_bps=Decimal(5))))
metrics = compute_metrics(result.equity_curve, result.round_trips)
print(len(result.fills), result.final_equity, result.digest())
```

A strategy can emit a `Signal` (the engine sizes it) or call `ctx.submit(...)` with an
explicit market, limit or stop order. [`examples/custom_strategy.py`](examples/custom_strategy.py)
shows explicit limit orders and `on_fill`.

## Architecture

```
            MarketFeed (iterable of Bar / Trade, time-ordered)
   HistoricalFeed (backtest)        ReplayFeed (paper, paced by a clock)
                         \            /
                          v          v
  +--------------------------- Engine ----------------------------+
  |  for each market event:                                       |
  |   1. execution.on_bar(bar)  -> Fill events (orders from       |
  |                                EARLIER events only)           |
  |   2. push the Bar itself                                      |
  |   3. drain EventQueue, ordered by (timestamp, sequence):      |
  |        Fill   -> Portfolio.apply_fill -> strategy.on_fill     |
  |        Bar    -> mark-to-market, equity sample, daily-loss    |
  |                  check -> strategy.on_bar                     |
  |        Signal -> sizing (allocation / per-trade risk) -> Order|
  |        Order  -> RiskManager.review -> execution.submit       |
  +---------------------------------------------------------------+
        |                    |                     |
   Portfolio            RiskManager        ExecutionHandler (Protocol)
   (Decimal)                                 `- SimulatedExecution
                                                (the only implementation)
```

| Module | Role |
|---|---|
| `events.py`, `eventqueue.py` | Immutable events; `(timestamp, sequence)` priority queue |
| `data/csvio.py`, `data/synthetic.py` | Validating CSV I/O; seeded GBM and OU generators |
| `feeds.py` | `MarketFeed` protocol, `HistoricalFeed`, `ReplayFeed` |
| `execution.py`, `costs.py` | `ExecutionHandler` protocol, fill simulator, fees, slippage |
| `portfolio.py` | Decimal accounting, equity curve, round trips |
| `risk.py` | Limits, risk sizing, daily loss halt |
| `strategy.py`, `strategies/` | Strategy base class and the two examples |
| `engine.py`, `backtest.py`, `paper.py` | Event loop and its two entry points |
| `metrics.py`, `report.py`, `cli.py` | Statistics, HTML report, command line |

### Backtest, paper and live are kept apart

| Mode | Market data | Execution | Status |
|---|---|---|---|
| Backtest (`run_backtest`) | `HistoricalFeed`, as fast as possible | `SimulatedExecution` | implemented |
| Paper (`run_paper`) | any `MarketFeed`; shipped: `ReplayFeed` | `SimulatedExecution` | implemented |
| Live | would be an exchange feed | would be a real `ExecutionHandler` | **not implemented, out of scope** |

The engine depends only on two protocols, `MarketFeed` and `ExecutionHandler`. A live
integration would have to supply both, and neither exists here: the `Mode` enum has no
`LIVE` member, and there is no networking, authentication or key-handling code in the
package. Paper mode never sends an order anywhere.

### How look-ahead is prevented

1. A bar's timestamp is its open time, and the strategy receives the bar only when it is
   complete.
2. Fills for a bar are computed *before* the strategy is shown that bar, from orders that
   already existed.
3. Independently of the engine, `SimulatedExecution` refuses to match an order against
   any market event whose timestamp is not strictly later than the order's.
4. `StrategyContext` exposes account state and order entry, and no market-data access.

`tests/test_engine.py::test_strategy_cannot_see_the_bar_it_is_filled_on` places an order
on a bar that closes at 100 when the next bar opens at 150, and asserts the fill is at
150, on the later timestamp, and that the strategy had been shown only the earlier bars
when the fill arrived.

### Fill and cost rules

- Market: next bar's open. Limit: the limit price if the bar trades through it, or the
  open if the bar gaps past it. Stop: the stop price if touched, or the open on a gap.
- Slippage applies to market and stop fills, never to limit fills. A fill with zero
  slippage is always at its reference price.
- Fill prices are not rounded by default: slippage is applied with exact decimal
  arithmetic, so an instrument quoted at 0.00001234 fills at 0.00001234. To model a
  venue's tick size, pass `--price-tick 0.01` (every symbol) and/or
  `--price-tick BTC-USD=0.1` (one symbol, repeatable); in the API use
  `EngineConfig(price_tick=..., price_ticks={"BTC-USD": Decimal("0.1")})`. With a tick,
  slipped buys round up and slipped sells round down, never in the trader's favour.
- Fee per fill = fixed + bps of notional, rounded half-up to the cent.
- With `--participation p`, fills on one bar cannot exceed `p` x bar volume in total;
  the remainder keeps working. Earlier orders are served first.

## Known limitations

- **Synthetic data only.** No real market data is shipped or has been used; the
  generators have no fat tails, volatility clustering, sessions, gaps or microstructure.
- **OHLC bars hide the path.** If a bar touches both a limit and a stop, or an order's
  price is touched but would not really have traded, the simulator cannot know. A
  protective stop submitted from `on_fill` becomes active on the *next* bar.
- **Simple cost models.** Slippage models are illustrative, not calibrated. There is no
  order book, queue position, latency, spread, borrow cost, funding, margin interest,
  dividends or corporate actions.
- **No margin model.** Cash may go negative (an entry is sized on the last close but
  filled at the next open; shorts are unconstrained unless you set risk limits).
- **Single currency, no multipliers.** Quantities are plain units; no futures/options.
- **Tick feeds** work through the Python API (`read_trades`, `on_trade`), not the CLI,
  and limit orders on ticks fill at the limit price when the print trades through it.
- **Reference strategies are single-symbol.** The engine handles several symbols, but
  SMA and Donchian keep one price window each.
- **Metrics use floats** (accounting does not) and annualise with a 365.25-day year
  inferred from the median bar spacing; pass `--periods-per-year` to override.
- **Determinism scope.** Engine results are exact for given input bars. The synthetic
  generators use `math.exp`/`random.gauss` before rounding to cents, so identical output
  across platforms relies on those agreeing to well within a cent; CI checks this on
  Ubuntu and Windows only.
- **Performance.** Pure Python and `Decimal`: fine for 10^4-10^5 bars, not for
  tick-by-tick research at scale. Not benchmarked.
- **Paper mode has only been exercised with the replay feed.** No live feed has been
  written or tested.
